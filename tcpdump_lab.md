# tcpdump: перехоплення та аналіз мережевого трафіку

Методичний матеріал для лабораторної роботи на стенді з 2–3 віртуальних машин.

---

## 1. Що таке tcpdump і навіщо він потрібен

**tcpdump** — консольна утиліта для захоплення (capture) пакетів мережевого трафіку на рівні мережевого інтерфейсу. Використовує бібліотеку `libpcap`, ту саму, що й Wireshark (яким, до речі, зручно відкривати файли, збережені tcpdump'ом).

Типові задачі, які він вирішує:
- діагностика мережевих проблем (втрати пакетів, розриви з'єднань, неправильна маршрутизація);
- аналіз протоколів (ARP, ICMP, DNS, TCP, HTTP та ін.) "з дроту";
- виявлення підозрілої активності (сканування портів, аномальний трафік);
- навчання — розуміння того, як насправді відбувається обмін даними в мережі.

### Встановлення

```bash
# Debian/Ubuntu
sudo apt update && sudo apt install -y tcpdump

# CentOS/RHEL/Fedora
sudo yum install -y tcpdump   # або dnf install -y tcpdump
```

Для захоплення пакетів потрібні права root (або встановлені capabilities `cap_net_raw`, `cap_net_admin` на бінарник).

## 2. Базовий синтаксис

```bash
tcpdump [опції] [вираз-фільтр]
```

### Найважливіші опції

| Опція | Призначення |
|---|---|
| `-i <iface>` | інтерфейс для прослуховування (`-i any` — всі інтерфейси) |
| `-n` | не резолвити IP в імена (швидше, читабельніше) |
| `-nn` | не резолвити ні IP, ні номери портів у назви сервісів |
| `-v`, `-vv`, `-vvv` | рівень деталізації виводу |
| `-X` | показати вміст пакета в hex + ASCII |
| `-XX` | те саме, але включно з Ethernet-заголовком |
| `-s 0` / `-s 65535` | захоплювати пакет повністю (snaplen), а не тільки перші 68/96 байт |
| `-c <N>` | зупинитись після N пакетів |
| `-w file.pcap` | зберегти сирі пакети у файл (для подальшого аналізу у Wireshark) |
| `-r file.pcap` | прочитати раніше збережений файл замість live-захоплення |
| `-A` | показати вміст пакета в ASCII (зручно для HTTP) |
| `-e` | показати Ethernet-заголовки (MAC-адреси) |
| `-D` | показати список доступних інтерфейсів |
| `-q` | скорочений (quiet) вивід |

### Фільтри (BPF — Berkeley Packet Filter)

| Вираз | Що фільтрує |
|---|---|
| `host 192.168.1.10` | трафік до/від конкретного хоста |
| `src host 192.168.1.10` | тільки трафік *від* хоста |
| `dst host 192.168.1.10` | тільки трафік *до* хоста |
| `net 192.168.1.0/24` | трафік цілої підмережі |
| `port 80` | трафік конкретного порту (в будь-якому напрямку) |
| `src port 443` / `dst port 22` | порт джерела / призначення |
| `tcp`, `udp`, `icmp`, `arp` | трафік конкретного протоколу |
| `tcp and port 80` | комбінація умов через `and` (або `&&`) |
| `host A or host B` | логічне АБО |
| `not arp` | заперечення |
| `tcp[13] = 2` | пакети з установленим прапорцем SYN (низькорівневий доступ до байтів заголовка) |
| `tcp-syn`, `tcp-ack`, `tcp-fin`, `tcp-rst` | зручні макроси для TCP-прапорців (див. приклади нижче) |

## 3. Топологія стенду

Рекомендована конфігурація на 3 віртуальних машинах в одній ізольованій мережі гіпервізора (VirtualBox: **Internal Network** або **Host-only**; або окремий `br0`/vSwitch):

```
        [ Internal/Host-only Network: 192.168.56.0/24 ]

  VM1 (client)        VM2 (server)         VM3 (sniffer)
  192.168.56.11       192.168.56.12        192.168.56.13
       │                    │                     │
       └────────────────────┴─────────────────────┘
                  спільний віртуальний свіч
```

- **VM1 (client)** — генерує трафік (curl, ping, ssh, dns-запити).
- **VM2 (server)** — приймає з'єднання (веб-сервер, ssh-сервер, DNS).
- **VM3 (sniffer)** — веде пасивне спостереження за трафіком.

> **Важливе застереження щодо перехоплення чужого трафіку.** У сучасних мережах на базі свічів (у т.ч. віртуальних) трафік між двома іншими вузлами (VM1↔VM2) *не* видно на третьому (VM3) за замовчуванням — свіч пересилає кадри лише адресату, а не всім портам (на відміну від hub). Щоб VM3 побачила чужий трафік, потрібне одне з:
> 1. **VirtualBox Internal Network у режимі "проміскуітет"** — увімкнути `Adapter → Promiscuous Mode: Allow All` для мережі. Це найпростіший варіант для навчального стенду.
> 2. **ARP-spoofing / MITM** (для окремого поглибленого завдання, лише в ізольованій лаб-мережі, з дозволу викладача) — інструментами на кшталт `arpspoof` + `sysctl net.ipv4.ip_forward=1`.
> 3. Двомашинний варіант простіший і достатній для базових вправ: сніфер запускається *на самому VM2 (сервері)* і бачить весь трафік, що приходить/іде саме з нього — цього повністю вистачає для розділів 4.1–4.6 нижче.

Для завдань 4.1–4.6 достатньо **двох ВМ** (client + server, де tcpdump запускається на server). Для завдання 4.7 (перехоплення "стороннього" трафіку) потрібні **три ВМ** з увімкненим promiscuous mode.

## 4. Практичні приклади (крок за кроком)

### 4.1. Перший запуск і базовий перегляд трафіку

На **VM2 (server)**:
```bash
sudo tcpdump -i eth1 -n
```
На **VM1 (client)**:
```bash
ping -c 4 192.168.56.12
```
На VM2 у виводі tcpdump з'являться ICMP echo-request/reply — переконайтесь, що бачите обидва напрямки.

### 4.2. Фільтрація за хостом і протоколом

```bash
# тільки ICMP до/від VM1
sudo tcpdump -i eth1 -n icmp and host 192.168.56.11

# тільки вхідний трафік від VM1
sudo tcpdump -i eth1 -n src host 192.168.56.11
```

### 4.3. Аналіз TCP-з'єднання (three-way handshake)

На VM2 підніміть найпростіший веб-сервер:
```bash
python3 -m http.server 8080
```
В окремому терміналі VM2 запустіть захоплення:
```bash
sudo tcpdump -i eth1 -n -vv 'tcp port 8080'
```
На VM1:
```bash
curl http://192.168.56.12:8080/
```
У виводі знайдіть послідовність:
```
Flags [S]        ← SYN від клієнта
Flags [S.]       ← SYN-ACK від сервера
Flags [.]        ← ACK від клієнта
Flags [P.]       ← дані (HTTP GET / response)
Flags [F.]       ← FIN (закриття з'єднання)
```
Це наочна демонстрація TCP three-way handshake і graceful close.

### 4.4. Перегляд вмісту пакета (HTTP у відкритому вигляді)

```bash
sudo tcpdump -i eth1 -A -s 0 'tcp port 8080'
```
Опція `-A` покаже ASCII-вміст — студенти побачать сирий HTTP-запит (`GET / HTTP/1.1`, заголовки `Host:`, `User-Agent:` тощо) — наочна ілюстрація того, чому HTTP без TLS небезпечний для передачі паролів.

Для порівняння — те саме з HTTPS (curl до https-сервера, якщо є) покаже лише зашифровані байти в `-X`.

### 4.5. Захоплення у файл і подальший аналіз

```bash
# захопити 200 пакетів повністю і зберегти
sudo tcpdump -i eth1 -s 0 -w /tmp/capture.pcap -c 200

# прочитати пізніше
tcpdump -r /tmp/capture.pcap -n

# прочитати з фільтром (фільтри працюють і при читанні файлу!)
tcpdump -r /tmp/capture.pcap -n 'tcp and port 8080'
```
Файл `.pcap` можна скопіювати (scp) на робочу машину і відкрити у Wireshark для графічного аналізу.

### 4.6. Аналіз DNS-запитів

```bash
sudo tcpdump -i eth1 -n -s 0 udp port 53
```
На VM1:
```bash
nslookup example.com 192.168.56.12   # якщо на VM2 піднято локальний DNS
# або просто
dig example.com
```
Продемонструвати структуру DNS-запиту/відповіді, TTL, тип запису.

### 4.7. (3 ВМ) Перехоплення трафіку між двома іншими вузлами

За умови промiскуітетного режиму мережевого адаптера:

На **VM3 (sniffer)**:
```bash
sudo tcpdump -i eth1 -n -s 0 host 192.168.56.11 and host 192.168.56.12
```
На **VM1** ініціюйте з'єднання до **VM2** (наприклад, `ssh user@192.168.56.12` або `curl`).

Студенти повинні побачити на VM3 повний обмін пакетами між VM1 і VM2, хоча сам VM3 стороною з'єднання не є. Це ілюструє принцип роботи мережевих сніферів/IDS у режимі "port mirroring" / SPAN-порту на реальному обладнанні.

### 4.8. Фільтрація за TCP-прапорцями (пошук сканування портів)

```bash
# показати лише пакети з установленим SYN, але без ACK (типово для сканування nmap -sS)
sudo tcpdump -i eth1 -n 'tcp[tcpflags] & (tcp-syn) != 0 and tcp[tcpflags] & (tcp-ack) == 0'
```
На VM1 (для демонстрації, за згодою — у власній лаб-мережі):
```bash
sudo nmap -sS 192.168.56.12
```
На VM3/VM2 студенти побачать характерну картину — багато SYN-пакетів на різні порти без відповідного встановлення з'єднання.

### 4.9. Статистика трафіку

```bash
# кількість пакетів кожного протоколу за 30 секунд
sudo timeout 30 tcpdump -i eth1 -n -q | awk '{print $NF}' | sort | uniq -c | sort -rn
```

## 5. Індивідуальні завдання для студентів

> Виконати на власному стенді (2–3 ВМ), для кожного завдання надати: команду tcpdump, скріншот/лог виводу, короткий письмовий аналіз (2–5 речень) — що спостерігалось і чому.

**Завдання 1 (базове).** Захопити ICMP-трафік між двома ВМ (`ping`). Пояснити структуру ICMP echo-request/echo-reply, показати поля TTL і sequence number.

**Завдання 2.** За допомогою фільтра виокремити лише вхідний трафік від конкретної IP-адреси і лише вихідний. Пояснити різницю виразів `src host` і `dst host`.

**Завдання 3.** Підняти на сервері `python3 -m http.server` і захопити повний HTTP GET-запит з опцією `-A`. Виписати з логу: метод, шлях, версію HTTP, заголовок `User-Agent`, код відповіді сервера.

**Завдання 4.** Захопити і проаналізувати TCP three-way handshake та коректне завершення з'єднання (FIN/ACK). Намалювати (від руки або в будь-якому редакторі) послідовність пакетів у вигляді діаграми обміну (sequence diagram).

**Завдання 5.** Захопити DNS-запит та DNS-відповідь. Визначити: тип запису (A/AAAA/CNAME), TTL відповіді, ID транзакції запиту та відповіді (переконатись, що вони збігаються).

**Завдання 6.** Зберегти 100 пакетів довільного трафіку у файл `.pcap`, потім прочитати цей файл двома різними фільтрами (наприклад, тільки TCP і тільки UDP) без повторного live-захоплення.

**Завдання 7 (просунуте, 3 ВМ).** Налаштувати проміскуітетний режим і з третьої ВМ перехопити трафік між двома іншими вузлами. Пояснити, чому це можливо/неможливо в реальній комутованій мережі без додаткових налаштувань (SPAN-порт, ARP-spoofing).

**Завдання 8 (просунуте).** Написати фільтр BPF, що виявляє пакети з установленим лише прапорцем SYN (без ACK). Запустити `nmap -sS` на сусідню ВМ і зафіксувати цю активність у логу tcpdump. Пояснити, чим SYN-скан відрізняється від повного TCP-з'єднання.

**Завдання 9.** Порівняти вміст пакетів HTTP-сесії (відкритий текст) і HTTPS-сесії (якщо є можливість підняти сервер із самопідписаним сертифікатом) — показати, що в другому випадку payload нечитабельний. Зробити висновок про доцільність шифрування.

**Завдання 10 (дослідницьке).** Виміряти й порівняти обсяг трафіку (кількість пакетів/байт) при передачі одного й того самого файлу через `curl` по HTTP і через `scp`. Пояснити різницю в накладних витратах протоколів.

**Завдання 11 (звітне).** Скласти короткий письмовий звіт (0,5–1 стор.) із поясненням, які саме можливості tcpdump і чому корисні адміністратору мережі та фахівцю з безпеки, з посиланням на власні спостереження з завдань 1–10.

## 6. Контрольні питання

1. Чим tcpdump відрізняється від Wireshark? У яких випадках доречніше використовувати саме tcpdump?
2. Що таке BPF-фільтр і як він відрізняється від фільтрів відображення (display filters) у Wireshark?
3. Чому для перехоплення "чужого" трафіку в комутованій мережі стандартний sniffing на випадковому вузлі не спрацює?
4. Що означають прапорці `[S]`, `[S.]`, `[.]`, `[P.]`, `[F.]`, `[R]` у виводі tcpdump?
5. Чим небезпечний перегляд HTTP-трафіку в незашифрованому вигляді для реальних систем (не лабораторних)?

## 7. Етичне й правове застереження

Перехоплення мережевого трафіку без явного дозволу власника мережі/системи є незаконним у більшості юрисдикцій (несанкціонований доступ до даних зв'язку). Усі наведені приклади призначені **виключно** для виконання в ізольованому навчальному стенді (власні ВМ, ізольована мережа), де студент має повний контроль і дозвіл на аналіз власного трафіку. Використання цих технік у реальних мережах без письмової згоди їх власника або адміністратора неприпустиме.
